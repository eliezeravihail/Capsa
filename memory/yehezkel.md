- 2026-08-01 · Closing a "pytest never touches the browser" gap for real: this env has Playwright pre-installed at `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` but only the NODE package (`/opt/node22/lib/node_modules/playwright`, needs `NODE_PATH=/opt/node22/lib/node_modules`); the Python `playwright` package was absent. Check both before assuming — `pip show playwright` first, fall back to node. Default `chromium.launch()` auto-resolved the right executable because the installed browser version matched the npm package version; only override `executablePath` when a project actually pins a different Playwright version.
- 2026-08-01 · A headless-browser SVG/PNG export can silently use DIFFERENT render parameters (cell/pad) than the core library's own defaults — cross-checking a live UI export against a Python "reference" sha256 by calling `to_svg()` with no args produced a spurious mismatch that looked like a regression. Root cause was my own test, not the product: the design deliberately keeps a core reference size (`DEFAULT_CELL/PAD`) separate from a UI display/export size (`config.board.CELL/PAD`) so exported image size is a UI concern, not a core one. Lesson: when binding a browser assertion back to a language-level source of truth, match the EXACT parameters the code path under test actually uses, not the library default — "verify don't guess" applies to your own harness's assumptions too.
- 2026-08-01 · `page.on('console')` + `page.on('pageerror')` catch `console.error()`/uncaught exceptions but NOT generic "Failed to load resource" 404 log lines (different CDP domain) — a "zero console errors" assertion built on these two events won't spuriously fail on an unrelated missing favicon, and also won't catch a real broken asset load; know which failure class each covers before trusting a null result either way.
- 2026-08-01 · A `try { doThing(); return; } catch (e) { setStatus(friendlyMessage) }` immediately followed (no `else`, no scope guard) by an unconditional fallback that ALSO calls `setStatus(...)` is a real, reproducible bug class: the catch's message is set then synchronously clobbered before paint, so a real user never sees it — invisible to any test that only checks the exception was caught, only visible to one that reads DOM state afterward. pytest structurally cannot see this (no DOM); a real headless-browser pass caught it in ~2 minutes. Found this exact shape in MazeForge's `app.js` `boot()` catch block — confirmed via `git show HEAD:web/app.js` byte-identical to a pre-refactor commit, so filed as a standing product defect (QA-1), not charged against the refactor under review. When a refactor's mandate is strictly "zero behavior change," a defect proven present before AND after does not fail that gate — but it must still be filed, not silently absorbed into the "pass."
- 2026-08-01 · Soft-assert harness pattern (record every check, never throw except on a setup precondition, print a final PASS/FAIL tally) surfaced far more in one run than a fail-fast script would have — a fail-fast run would have stopped at the first (spurious, harness-side) SHA mismatch and never reached the worksheet/theme/permalink checks in the same pass. Worth the small amount of extra bookkeeping every time a script drives a multi-step user flow.
- 2026-08-01 · Reproducing "click a button that calls `window.open('', '_blank'); win.document.write(html); win.print()`" in Playwright: capture the popup via `context.waitForEvent('page')` fired concurrently with the click; `win.print()` did NOT hang headless Chromium in this environment (resolved immediately) — but wrap the wait in a race against a short timeout anyway before trusting that in a new environment.
